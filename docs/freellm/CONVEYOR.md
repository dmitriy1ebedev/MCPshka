# Ночной FreeLLM-конвейер

В 0.16.5 `fixes_night mode=manual` запускает bounded job ночью (22:00–06:00)
при тихом H96. После `job_wait` результат читается через `job_output`.
Инструмент выбирает все открытые P1–P3 MCPshka/Lane/DIAG: P1 и повторяющиеся
сбои первыми. Сначала план, затем патчи по шагам с ограниченным контекстом
и фильтром секретов. Изменения, commit и project_test остаются в fix/<card>.
Серверный ночной цикл запускает bounded job при load1 < 6; мутаций хоста нет.

Утром `fixes_review action=list` показывает карточку, diff, commit и тест.
`action=accept cards=[...] path=<release-worktree> lease_token=...` переносит
зелёную пачку в чистую ветку выпуска; `action=reject cards=[...] reason=...`
записывает причину в карточку. Всем вызовам нужен `idempotency_key`.
Версию поднимает выпускающий чат. MOTD показывает короткий итог очереди.

Автоматическое вливание запрещено: только утренний fixes_review, по одному
проекту в его release worktree. Потерянный ответ теста восстанавливается
по прежнему ключу через fixes_review.

Ниже — устройство шлюза и ручная диагностика отдельных шагов.

## Каталог и живость

Шлюз использует только существующий /etc/mcpshka/llm.json и его key_file (0600).
Ключи не передавать в скрипт или карточку. API проверен по
[документации FreeLLMAPI](https://github.com/tashfeenahmed/freellmapi/blob/main/docs/en/api/01-rest-api.md#model-listing):
GET /v1/models с той же авторизацией, что POST /v1/chat/completions.
Каталог может содержать неподключённые модели и виртуальные auto/fusion;
наличие в списке само по себе не доказывает работоспособность.

```js
return llm.models();
```

Возвращаются конкретные id, execution_status провайдера, локальные state
(unknown/alive/dead), checked_at и last_error. Каталог и результаты проб кешируются
на health_cache_minutes (по умолчанию 5). Просроченное наблюдение становится
unknown; last_error остаётся исторической справкой до следующей пробы.
models() не запускает массовый опрос всех провайдеров.

Перед отправкой задания неизвестная модель получает одну короткую пробу
«Reply OK.» с max_tokens=8. Ошибка, пустой ответ или таймаут исключают её
на срок кеша. Указанная model идёт первой (с обязательной пробой при unknown),
затем остальные живые модели; имени вне каталога запрос не отправляется. На каждую модель — максимум одна проба и
одна попытка задания за вызов. После ошибки задания, включая 503/таймаут,
выбирается следующая. Все попытки укладываются в общий бюджет без повторов одной модели.
Тело HTTP-ошибки очищается от секретов и ограничивается 512 байтами.

## Параметры

| Параметр | По умолчанию | Диапазон |
| --- | ---: | --- |
| llm.json timeout_seconds: одна попытка задания | 90 с | 1–300 с |
| llm.json budget_seconds: каталог + пробы + все задания | 180 с | 1–600 с |
| llm.json probe_timeout_seconds | 5 с | 1–15 с |
| llm.json health_cache_minutes | 5 мин | 1–60 мин |
| code_run timeout_seconds: весь скрипт | 20 с | 1–600 с |
| llm.compare count | 3 | 1–5 |

У llm.ask/compare timeout_seconds и budget_seconds переопределяют конфиг;
родительский deadline всегда действует. Для LLM явно задавать code_run
timeout_seconds=180 (один ответ) или 300 (сравнение с budget_seconds=290).
Это снимает прежний предел 60 с, но не продлевает таймаут транспорта клиента:
клиент также должен допускать длительный вызов.

## Отбор и сравнение

1. Получить карточку; взять её project и пути файлов, которые **нужно изменить**.
   Если другого репозитория требует текст задания, явно выставить
   requires_other_project=true. Не включать историю карточки и служебные токены.
2. До чтения контекста и обращения к LLM вызвать:
   `llm.scope({project, paths, requires_other_project}, "mcpshka", "/root/repos/mcpshka")`.
   Только eligible=true допускает карточку. Иное поле проекта, абсолютный путь
   снаружи root или относительный ../ дают requires_other_project=true и reason.
   PRJ-005 (tabl) и MCP-198 (workflow go2rtc) пропускаются с этой причиной.
   Упоминание другого проекта в диагностике MCPshka само по себе не запрещено.
   Это проверка метаданных, не замена проверкам путей/lease инструментов записи.
3. Прочитать минимальные исходники и тесты. Получить каталог; не ограничиваться
   auto и одним угаданным именем.
4. Вызвать code_run с обычным timeout_seconds=20 и скриптом:

```js
const selection = llm.scope(
  {project: "mcpshka", paths: ["internal/example/file.go"]},
  "mcpshka", "/root/repos/mcpshka"
);
if (!selection.eligible) return {status: "skipped", reason: selection.reason};
return llm.compare(
  "Предложи минимальный unified diff и регрессионный тест; объясни изменение.",
  store.get("card-context"),
  {count: 3, timeout_seconds: 90, budget_seconds: 290}
);
```

5. Начиная с 0.16.4 llm.compare, llm.ask и llm.models сразу возвращают
   `{job: {id, state, ...}, next: "job_wait, then job_output"}`. Держать `job_wait`
   для `job.id` до terminal, затем читать JSON через `job_output` (с пагинацией
   по `next_cursor`). Внутри результата code_run готовых ответов ещё нет.
   Отмена клиентского code_run не отменяет уже созданный LLM-job; явная
   отмена — `job_cancel`. Работает один LLM-job одновременно, бюджет до 600 с;
   после перезапуска незавершённый read-only job получает failed и его можно
   запросить заново. Тела запросов и исходные ошибки не пишутся в argv/журнал.
   Это устраняет обрыв клиента MCP на 60 с: увеличивать синхронный timeout
   code_run до 180–300 с больше не нужно.

   Проверить complete, requested, replies и failures из JSON job_output. Каждый reply содержит
   text, фактическую model (поле ответа провайдера; при его отсутствии — id
   запроса), redactions и redaction_types. Повтор одного фактического model
   не засчитывается за отдельный голос. Неполный набор не называть кворумом.
6. Контролёр сравнивает ответы: совпадает ли причина, покрыты ли края тестом,
   нет ли новых зависимостей/ослабления защиты/правок чужого проекта. Выбирает
   минимальный корректный diff. Согласие моделей не является тестом.
7. Применить diff с lease, выполнить точечный project_test, review diff и commit.
   В журнал ночи записать карточку, причины пропуска, модели, типы/число
   редакций, длительности, проверки и результат. Не записывать секреты,
   исходные тела запросов или ошибок.

Один ответ:

```js
return llm.ask("Объясни ошибку", store.get("card-context"),
  {timeout_seconds: 90, budget_seconds: 170});
```

В JSON завершённого llm.ask текст доступен как .text; объект также содержит модель и статистику редакций.

## Редакция и первый прогон

Вместо EGRESS_REFUSED для всего запроса секретные фрагменты заменяются
на [REDACTED:тип]; незатронутый текст отправляется. Известные значения и их
12-символьные префиксы удаляются до шаблонов; при совпадении префикса удаляется
и оставшийся токенный хвост. Целый блок private key удаляется вместе с телом.
Строгий Filter для HTTP/PDF сохраняет отказ при обнаружении секретов.

Журнал NIGHT_2026-11-18.md (7644c5b) фиксирует для MCP-204 assignment/known_secret,
для MCP-206 assignment/high_entropy/known_secret. Он не хранит совпавшие значения,
поэтому точный исторический known_secret без исходной среды установить нельзя.
В коде воспроизведены источники ложных срабатываний:

- имя TestExecKeyUnwrapsAndSkipsRouted выглядит высокоэнтропийным;
- token = os.Getenv и другие ссылки на поля/функции выглядят как присваивание;
- сборщик известных секретов раньше искал секретное слово во всём env-присваивании,
  включая публичное значение, и считал key_file/token_path самими ключами.

Первые два случая теперь вырезают только фрагмент, не блокируют карточку.
Сборщик env проверяет имя поля; абсолютные/явные относительные пути в полях
*_file/*_path считаются метаданными. Реальные значения ключей, токенов и паролей
остаются под литеральным и шаблонным фильтрами. Тесты используют только
синтетические секреты, а не production-ключи.
