# MCPshka 0.12.0 — «Документы и облака»

Задача владельца 12.11.2026: закрыть карточки проблем, упростить подключение Google Drive, перепроверить Яндекс.Диск и Dropbox, научить MCPshka работать с документами Office и LibreOffice (таблицы, текст, макросы), разобраться с «1 не авторизован» в ChatGPT и с письмами MosHub о падении конвейера.

## Документы: `doc_inspect`, `doc_edit`, `doc_preview`

MCPshka читает и меняет документы через LibreOffice на H96 (пакет `internal/officedocs`, работник `office.py` на Python-UNO, одно ограниченное задание на запуск).

- Форматы: таблицы ods, xlsx, xlsm, xls, csv; текст odt, docx, doc, rtf; презентации odp, pptx; простой текст txt, md, json и подобные; вывод также в pdf, html, png.
- `doc_inspect` — листы, занятая область, значения и формулы ячеек; абзацы со стилями и таблицы; текст слайдов; все модули макросов с исходным текстом. Макросы открываемого файла не исполняются.
- `doc_edit` — операции по порядку: ячейки и формулы, оформление (шрифт, цвет, заливка, выравнивание, числовой формат, рамки, объединение), ширина столбцов, строки и столбцы, листы, закрепление, автофильтр, диаграммы; для текста — абзацы со стилями, замена, таблицы, поля страницы; макросы — записать модуль, привязать к событию документа, запустить.
- Чего нет в операциях (сводные таблицы, условное форматирование, элементы форм) — делает `script`: код Python-UNO с открытым документом.
- Исходный файл не меняется: результат — новый файл в папке запуска. Цикл «изменил → проверил → поправил»: `doc_edit` → `doc_inspect` или `doc_preview` (картинка первой страницы) → снова `doc_edit` по `output.path`.
- Исполнение кода (`script`, `macro_run`) требует окна Face ID; правка содержимого и запись текста макроса — нет.
- Ограничение LibreOffice: новые и изменённые макросы сохраняются только в OpenDocument (ods, odt, odp). В файлах MS Office остаётся тот VBA, с которым файл пришёл; `doc_edit` предупреждает об этом в `warnings`.

Путь файла: `storage_download` → `local_path` (теперь `/var/cache/mcpshka-documents/<id>/<имя>`, читается сервисом) → `doc_inspect` / `doc_edit` → `storage_upload document=<output.path>` или `artifact_get`. Файл из чата — `artifact_upload_*` и `artifact_id`.

На хосте: доставлены `libreoffice-writer`, `-impress`, `-draw` (был только Calc); каталогу `/var/spool/libreoffice/uno_packages/cache/uno_packages` возвращены права 755 — с 0700 LibreOffice падал у любого пользователя, кроме root.

## Облака

- `storage_connect` всегда отвечает ссылкой. Страница сама ведёт по шагам: если у облака ещё нет приложения OAuth — показывает, что создать, точный адрес возврата и форму для ключей. Ключи вводятся в браузере и в чат не попадают; `storage_oauth_app_set` остаётся для совместимости.
- Яндекс.Диск и Dropbox подключаются и без своего приложения — «быстрый» путь через приложение rclone (тот же, что на странице «Подключения»).
- Google Drive: общий ключ rclone отключают в 2026 году, и он упирается в лимиты (`rateLimitExceeded`, MCP-165), поэтому для Drive — только своё приложение. Запрашивается весь Диск (`drive`), а не `drive.file`: иначе MCPshka не видит файлы владельца. `storage_providers` помечает учётку на общем ключе.
- `storage_auth_status provider=…` делает живое чтение облака: `connected` или `credential_rejected` с причиной, а не «credential_present, unverified».
- Сообщения об ошибках называют `storage_connect`, а не `rclone authorize`; пустой фрагмент «: ,» убран.

Проверено 12.11: Dropbox — токен обновляется, чтение проходит; Google Drive — чтение проходит, но учётка на общем ключе rclone (нужно переподключить); Яндекс.Диск и OneDrive не подключены.

## «1 не авторизован» в ChatGPT

`capabilities_bootstrap` показывал `denied_count: 1` — служебный `broker_install` (нужен один раз при установке, выдать на него право нельзя). Теперь он не считается отказом. Давно молчащий клиент (последний `tools/list` старше 72 часов) помечается `historical` и не портит здоровье каталога (MCP-181).

## MosHub

Письма «конвейер завершился неудачно» шли по двум причинам:

- 10–11.11 — гонка данных в тесте `TestOwnerToolsProxyScopesAndLease` (MosHub гоняет `-race`); тест исправлен.
- с 12.11 — все общие раннеры MosHub выключены: конвейер висел часами и падал как `stuck_or_timeout_failure`. Теперь снимок не публикуется на MosHub, пока нет раннера в сети (`no_online_runner`), — нет конвейера, нет письма.

GitHub писем не шлёт, потому что прогонов там нет: он подключается только как запасная площадка, когда GitVerse недоступен.

## GitHub: письма «PR run failed»

С 12.11 на GitHub падали три проверки каждого выпуска (0.11.9, 0.11.10):

- `checks (race)` — та же гонка в тесте `TestOwnerToolsProxyScopesAndLease`;
- `checks (release)` — тест `test_production_proof_…` требовал, чтобы файл блокировки принадлежал root, а раннер GitHub работает не от root;
- `admin-recovery` — с MCP-164 (10.11) root держит долгоживущий `sqlite3` для своей базы; в фикстуре теста его WAL-файлы оставались root-овыми после передачи базы сервисному пользователю. В проде база принадлежит сервису, дефект был только в тесте.
