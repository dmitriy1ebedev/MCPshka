# MCPshka 0.9.6 — 2026-11-09

## Брошенный lease больше не держат чужие читатели (MCP-155, владелец 09.11: «критично для всех проектов»)
- Снятие зависшего lease (`project_lease_admin_stale_preview/release`) отказывало, если любой процесс держал открытым файл проекта. Desktop Commander с 05.11 держал прочитанные (и уже удалённые) файлы Lane → ChatGPT 8 часов каждый час писал «нужна админ-сессия».
- Теперь файл, открытый только на чтение, lease не держит (читатель не меняет проект). Держат по-прежнему: рабочая папка процесса внутри проекта, файлы на запись, открытые папки, отображённые в память файлы.
- Отказ называет системную службу-держателя и шаг: `service_restart <служба>`.
- `mission_report`: молчащий >30 мин держатель без заданий → «Project held by · … (silent …, no jobs)» и единственный шаг владельца (Face ID + stale_preview/stale_release) — вместо одинаковых ежечасных проверок.
- `mission_status`: остановленная работа без новостей >72 ч (прогоны roadmap_run 02–04.11) уходит в `archived`, а не держит каждую миссию в degraded.

## Файлы и CI
- `fs_write` в новую папку больше не падает на предпроверке `fs_stat` «resolve workdir» (MCP-156): несуществующие папки под разрешённым корнем — `missing`.
- `forge_ci path=`: подсказка «следующий шаг» — `forge_ci mode=status` (раньше — несуществующий `project_ci_status`).
- `phase_gate` принимает зелёный GitVerse CI того же HEAD (`forge_ci path=`) вместо локального sealed-теста — тяжёлые тесты проектов уходят с приставки; отменённый/таймаутный sealed-тест помечается «не ошибка кода», а не FAIL (отчёт Lane 09.11).
- Публичный путь `/runner/*` в `packaging/tunnel/mcpshka-faceid.caddy` (на H96 открыт 09.11).

## DIAG traffic-route: жёсткие границы (MCP-153, блокер DIAG P34)
- Захват ≤300 с (было 900), один pcap под лимитом ядра RLIMIT_FSIZE 32 МиБ — без кольца `-C/-W`, ранние пакеты не перезаписываются; упор в лимит — `ended_by: byte_cap`.
- MAC клиента перепроверяется каждые 10 с: ответ с другого устройства → захват остановлен, `FAILED`, `target_identity_mismatch_during_capture`.
- Новый `traffic_route_cancel` (идемпотентный): воркер завершает захват сам; мёртвый или зависший — группы воркера/tcpdump/conntrack добиваются (проверка cmdline против повторного PID). Итог: `CANCELLED`, `ended_by`, `pcap_bytes`, квитанция `cleanup.all_stopped`. Брокер: форма `stop --run … --root … --json`.
- Тесты: `packaging/native/test_diag_traffic_route.py`, `TestDiagTrafficValidation`.

## Облака целиком (владелец 09.11: «с любыми файлами, а не только в своей папке»)
- `storage_*` работают со всем облаком (Google Drive, Dropbox, Яндекс, OneDrive): путь от корня, пустой путь — корень. Как и раньше: без перезаписи (`--immutable`), без безвозвратного удаления — `storage_trash` переносит в `MCPshka/.trash`; `MCPshka/.trash` и `MCPshka/backups` напрямую не пишутся.
- Раньше всё жило в папке `MCPshka/`, которой в только что подключённом облаке нет → любой `storage_list` падал немым `FENCED_UNKNOWN`.
- Ошибка воркера хранилища теперь доходит до ответа («storage request failed: …»), а не теряется.

## Узлы и CI
- «Узлы»: статус — по последней «Проверить связь» (подключено / нет связи с причиной / не проверен), а не всегда «подключено». Сменившийся ключ хоста называется прямо: сверить отпечаток с консолью провайдера, только потом принять.
- `forge_ci mode=status path=`: для упавших заданий — `failures` с выдержкой лога до первой ошибки (≤40 строк), чтобы ИИ видел причину, а не «unit: failure».
- Раннер (`agent.py`) сам завершается после 10 мин без задач (решение владельца 09.11) (`--idle-exit MIN`, 0 — никогда): облачная IDE засыпает и не тратит бесплатные часы, автозапуск `.devcontainer` поднимает раннер при следующем открытии. Первый боевой раннер — GigaIDE (amd64, 4 ядра), 09.11.
- Оптимизация под храповик archlint без поднятия лимитов: обработчики traffic_route status/report/cancel — один вызов брокера; проверка MAC — одно условие.
- Раннеры и окружение (MCP-157): проект объявляет, что нужно его тестам, файлом `.runner-needs` (у MCPshka — `sqlite3 pyyaml`); раннер сообщает свои возможности и сам ставит недостающее, если есть sudo без пароля; задача уходит только раннеру со всеми нужными возможностями, иначе `NO_RUNNER` → `project_test` на H96. Первый прогон на GigaIDE упал не из-за кода, а из-за отсутствия `sqlite3`.
