# MCPshka 0.9.5 — 2026-11-08

## Контейнеры на веб-морде (владелец 08.11: «нативно в самой MCPshka, просто, удобно, быстро»)
- Страница `/connections/containers` (ссылка с «Подключений»), та же Face ID-сессия. Все контейнеры H96 из живого Docker — без ручного списка: состояние, здоровье, рестарты, CPU/RAM, compose-проект; упавшие сверху. Кнопки «Запустить / Перезапустить / Остановить» и хвост логов (≤300 строк, без цветовых кодов), автообновление раз в 15 с.
- Пакет `internal/containerctl`, семейство брокера `containers`. Действует только на существующий сейчас контейнер, команды — только start/stop/restart/logs.
- Самолечение: если Docker отказывает в старте «…/moby/<id>: file exists» (мёртвая задача containerd, так упал Zigbee2MQTT 08.11 18:47), каталог мёртвой задачи переносится в `/run/containerd-stale/` (не удаляется) и старт повторяется. Задачу с живым процессом не трогает.
- `docker_action start` разрешён для контейнеров из списка перезапуска (старт остановленного не шире рестарта); stop — по-прежнему только по списку мутаций.

## Миссии больше не блокируют сами себя (DIAG из ChatGPT, 08.11)
- Шаг миссии блокирует только настоящий отказ: вердикт blocked, неисправная обязательная зависимость, unknown или отсутствие данных. Устаревший замер нагрузки и инструменты без внешних зависимостей — не повод.
- Фоновое обслуживание миссий: бюджет `budget.Phase(45s)` вместо 5 с, повторная проверка BLOCKED-миссии не чаще раза в 2 мин. Раньше полный preflight 20-шаговой миссии каждые 10 с не укладывался в 5 с, таймауты с 09:00 шли непрерывно и сами делали подсистему миссий degraded → новая миссия DIAG стояла BLOCKED на всех 20 шагах.

## Ресурсы, Код, IDE — нативно в веб-морде (владелец 08.11, работает только с iPhone/iPad)
- Общая рамка страниц (`pages_html.go`): навигация Подключения · Ресурсы · Контейнеры · Код · IDE · Раннеры · Проблемы, CSP с nonce, без кеша.
- Прокси инструментов `/connections/api/tool`: страница вызывает инструменты MCPshka от имени `owner-web` (Face ID-сессия) — только белый список (`fs_*` чтение/запись, `git_status/diff`, `project_commit/test/context`, `job_*`, `health_snapshot`, `host_triage`, хранилище); `exec_start`, выпуск, `tool_invoke` недоступны. Аренда проекта для правки хранится на сервере в сессии и подставляется только для своего проекта; выход из сессии её отпускает.
- «Ресурсы»: нагрузка, память, диск, температура, прогноз диска, давление очереди тяжёлых задач, контейнеры по памяти, крупное на диске, подсистемы — раз в 30 с.
- «Код»: проекты из `/root/repos`, дерево, просмотр/правка (SHA-закреплённая запись ≤64 КиБ), «Править/Отпустить» через аренду (если проект ведёт ИИ — только просмотр), изменения + diff, коммит выбранных, тесты через очередь.
- «IDE»: варианты для iPad (Код, GigaIDE Cloud, code-server только дома — наружу не выставлен, т.к. root), адрес MCP и готовые конфиги VS Code / Cursor / Claude Code / Codex / JetBrains. Мозг OAuth «IDE»: loopback-возвраты `http://127.0.0.1:<порт>/…` и `cursor://anysphere.*` (без userinfo/query/fragment); каждый вход — Face ID.

## Облачные раннеры (владелец 08.11: «как принято в мировом сообществе», в 0.9.5)
- Pull-раннер по образцу GitHub Actions self-hosted / GitLab Runner: пакет `internal/runnerhub`. Раннер сам ходит к MCPshka по HTTPS (`/runner/*` на публичном адресе) — без входящих портов и SSH.
- Регистрация одноразовым токеном (страница «Раннеры», Face ID, живёт час) → свой ключ раннера (хранится только SHA-256). Одна задача под аренду 90 с с пульсом каждые 30 с; раннер уснул/пропал → задача сама в очередь (до 3 попыток); никто не взял за 10 мин → `NO_RUNNER` с подсказкой «project_test на H96».
- Задача = полный SHA коммита (`git archive`) + профиль `go-test` / `go-vet` / `go-build` с пакетами — никакой произвольной команды. Результат — хвост вывода ≤256 КиБ с SHA-256, `trust: UNTRUSTED`: ускоряет поиск ошибок, ворота выпуска по-прежнему `project_test`/CI.
- Раннер — один файл Python (стандартная библиотека, `/runner/agent.py`); нет Go — сам скачивает версию из `go.mod`. Подключение — одна команда в терминале облачной IDE; автозапуск — `.devcontainer/devcontainer.json` `postStartCommand`.
- Инструменты `runner_task` / `runner_status` и справка `mcpshka_guide topic=runners` — одинаково понятны любому ИИ (ChatGPT, Claude, Kimi, DeepSeek…). Страница «Раннеры»: команда подключения, автозапуск, раннеры (ждёт/работает/спит, «Отключить»), задачи с выводом.

## Ещё в 0.9.5 (владелец 08.11: «всё, что на потом, — в 0.9.5»)
- «Ресурсы» → «Почистить»: кэш сборки Go (не во время сборки/теста), мусор Docker (только висячие образы и кэш сборки — рабочие образы, контейнеры и тома не трогаются), журнал systemd до 200 МБ. Размер мерится вживую до и после, пакет `internal/hostclean`, семейство брокера `cleanup`; кнопка — в Face ID-сессии, с подтверждением.
- `mission_report`: кто сейчас держит проект (`holder`: free / владелец аренды) и 5 последних коммитов (`recent_commits`). Основной чат и ежечасная задача видят одно и то же; занят другим — ждать или работать на чтение, не бороться за аренду.
- CI GitVerse для любого проекта H96 — тем же `forge_ci` (без нового инструмента): `forge_ci provider=gitverse mode=publish|status path=/root/repos/<проект>`. MCPshka сама создаёт ПРИВАТНЫЙ репозиторий (публичный — отказ, пуш не делается), ставит его `main` ровно на коммит (зеркало, force: история хранится на H96; владелец 08.11) и читает CI (NO_RUN/RUNNING/PASS/FAIL). Пакет `internal/projectci`, токен — из файла, в вывод не попадает. DIAG и Lane заведены приватными (dmitriy_1ebedev/diag, /lane); у DIAG — `.gitverse/workflows/ci.yml` (go vet, go test, python-тесты).
- `fs_write` сам создаёт недостающие папки (до 8, только там, где разрешена запись; при отказе записи пустые папки убираются) — «lstat: no such file» при создании `.gitverse/workflows/ci.yml` больше не упор.
- Удалён неиспользуемый `internal/remoterunner` (ноутбук по SSH через Tailscale): его заменяет pull-раннер, работающий и под Амнезией.
- Справка: `runners` — оба пути разгрузки H96 (CI GitVerse, раннеры); правило 14 в `rules`. Одна для всех ИИ: ChatGPT, Claude, GigaChat, Kimi, DeepSeek…
- MCP-154: `job_cancel` полного теста во время подготовки песочницы терялся, и тест всё равно запускался (занимал очередь ~35 мин). Отмена теперь «липкая»: запоминается и применяется при каждом следующем наблюдении до конца задачи.
