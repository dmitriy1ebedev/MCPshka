
# Выпуск MCPshka

## Выпуск любого другого проекта (Lane, DIAG, свои)

Один путь для всех: `project_release` (статус — `project_release_status`). Проект сам описывает выпуск в `.mcpshka/release.json` (schema `mcpshka.release/v1`): шаги `argv` без shell, `root` где нужен root, `expect`/`fail`/`retry_seconds` для ожидания, `capture` для значений, `rollback` + `rollback_from` для отката, подстановки `{commit} {version} {root} {name}`. Новый проект = новый файл рецепта, правка MCPshka не нужна.
1. Нет рецепта — напиши его в ветке проекта (установка, проба работающей команды, откат), закоммить, влей в main, CI на точном коммите.
2. `project_release` (Face ID окно, commit с main, version). Новый или изменённый рецепт отвечает `RECIPE_NOT_APPROVED` с готовым планом `approved_task_prepare`: дай владельцу ссылку Face ID и продолжай другие пункты; после подтверждения повтори с новым ключом.
3. «Установлено» — только `project_release_status` = `INSTALLED`; затем проверка Exit пункта заданием MCPshka.
Ребут хоста рецептом не делается: если новая раскладка вступает в силу только после загрузки, это решение владельца (`host_reboot_plan`).

## Сначала выбери штатный маршрут

Когда владелец просит «обнови MCPshka», «выпусти версию», «выпусти сам» и в защищённой ветке имеется **чистый, зафиксированный HEAD**, основной путь — серверный автовыпуск **`release_apply action=queue`**. Он сам ведёт CI → защищённую интеграцию → paired ARM64 build (controller + broker) → установку с откатом → `project_verify`. Не заставляй пользователя проводить эти шаги вручную и не останавливайся на первой ошибке альтернативного ручного пути.

1. Начни с `project_context` (ветка, полный 40-hex commit, git clean, lease/jobs), `admin_session_status`, версий в `server.go` и `health.go`, `release_apply_status(version)`. При необходимости смотри точную сигнатуру через `tool_resolve(goal="автоматический выпуск MCPshka")`. Если есть активная очередь **этой версии**, наблюдай **существующую** `release_apply_status.queue`; не создавай дубликат и не отменяй чужую очередь. Если git dirty, исходный коммит не подготовлен, CI уже упал либо чей-то writer ещё меняет ветку — сначала безопасно исправь/закоммить/согласуй, не закрепляй заведомо неверный SHA.
2. С активным Face ID выполни один `release_apply` с `action="queue"`, `version`, `branch`, `commit` (полные 40 hex), `store_id` защищённого репозитория, `admin_session_id`, неизменным `idempotency_key`. Для queue-only входные `build_permit` и `test_permit` пустые: сам сервер получит и проверит их по точному коммиту; **не подставляй выдуманные разрешения**. Команда выдаёт `QUEUED`, что означает только постановку, а не успешную установку.
3. Наблюдай `release_apply_status(version).queue`: `QUEUED → SHIP → BUILD → STAGE → APPLY → VERIFY → DONE`. Утверждать «версия установлена и принята» можно только при `queue.stage=DONE`, `installed_version=version` и успешной независимой `project_verify(expected_version=version)`; проверь broker/tunnel, DNS/HTTPS, критические контейнеры, rollback. Состояния `WAITING_FACEID`, `FAILED`, `UNKNOWN` требуют разбора исходной записи/сохранённого ID, не повторного запуска под другим ключом.
4. Если прямой `integration_ship` заблокирован политикой клиента/платформы, это не доказывает неисправности уже зарегистрированного разрешённого **самостоятельного** серверного маршрута. Проверь наличие `release_apply action=queue` через документацию и `tool_resolve`, его собственные Face ID/CI/review/rollback-gates. Не обходи отказ через RDC, raw Git, bash, `tool_invoke` или подмену исполнителя. Если отдельный разрешённый путь тоже отказал — сохраняй чекпойнт, оформи карточку, сообщи HOLD.

## Ручной выпуск (когда автовыпуск объективно неприменим)

Нужен активный Face ID (`admin_session_status`; нет — `admin_session_prepare` → `admin_session_begin`, ссылку дать в конце хода). Store защищённого репо: `f4bf4ece6766df20cb72d59f3ab2c4e8`.

1. **Подготовка ветки.** `const Version` в `internal/mcpserver/server.go` и **та же** `const BrokerVersion` в `internal/rootbroker/health.go` (иначе CI: TestHealthBrokerVersionIsControllerVersion), `docs/releases/RELEASE_<v>.md`, коммит. Свои сборки и тесты — только `project_build`/`project_test`; полный sealed project_test — после коммита на чистом HEAD.
2. **ROADMAP до вливания**: реестр багов, «Очередь» (меняет SHA ROADMAP — поэтому сейчас).
3. **Вливание и CI одним вызовом:** `integration_ship path=/root/repos/mcpshka branch=<ветка> commit=<sha> evidence=auto` (с 0.9.8; `auto` = GitVerse, а при сбое самой площадки — её перезапуск и параллельно GitHub, засчитывается первая прошедшая; стадия `CI_FALLBACK`) — повторять тот же вызов каждые ~60 с, **не реже**. MCPshka сама публикует снимок на GitVerse, раздаёт его на MosHub и GitHub и ждёт прогон: `CI_PUBLISHED` → `CI_RUNNING` → запечатывание. `CI_FAILED` — в `detail` выдержка из лога: исправить, новый коммит, ship с новым коммитом (тот же не перезапускать); полная выжимка — `forge_ci provider=gitverse mode=status` (`failure.jobs[]`). Воркер доказательства ждёт fence от ship, лимит его юнита 3 мин — пропуск опроса убивает попытку (тогда attempt+1). Между enqueue и PUBLISHED ROADMAP не править. На `READY_FOR_APPROVAL` → `integration_approve(store_id, permit_id)` → `integration_ship` с `approval_id` до `PUBLISHED`; после него MCPshka сама зеркалит main на GitVerse, GitHub и SourceCraft. Только GitHub — `evidence=ci` (снимок, PR, прогон); только GitVerse — `evidence=gitverse`. Полный набор на GitVerse идёт тремя параллельными шардами (`release-shard-0..2`), шлюз — задание `release-suite`. Упал конвейер MosHub — `forge_ci provider=moshub mode=rerun`.
4. **Таймауты не подбирать:** бюджет любого задания MCPshka считает сама (история p95, нагрузка, продление при прогрессе, сторож тишины, потолок 6 ч); решение видно в `plan.reason`. Явный `timeout_seconds` нужен, только если прогон заведомо дольше прошлых.
5. **Основной маршрут — проверенный GitHub CI artifact + signed paired deploy.** После protected integration pin точный `main` commit, source tree/digest и успешно завершённые `release`, `race`, `fuzz`, `build`, `release-arm64` GitHub Actions. Не принимать название workflow, зелёную кнопку без run ID или GitVerse snapshot за CI provenance; нужны authenticated run, artifact ID и SHA-256 controller+broker.
6. **Подготовка пары:** `release_prepare source=github artifact_url=<short-lived oaiusercontent HTTPS URL> version=<new> current_version=<installed> source_digest=<pinned> receipt=<operator-verified CI v2>`. Не раскрывать подписанный URL в логах/аргументах. `release_status(job_id)` до terminal success, сверить prepared candidate, broker companion, receipt, release plan. Подготовка не устанавливает версию и не предоставляет право на деплой. При утрате ответа — `mutation_probe` оригинального ключа / `release_status`, без двойной подготовки.
7. **Установка пары:** `project_deploy path=/root/repos/mcpshka candidate_path=<exact prepared candidate> expected_version=<new> idempotency_key=<stable>`. Только с валидным подписанным v2 планом, проверенными pinned образами controller+broker, защитой работающего MCP-туннеля и доступным rollback. Сохранить `deployment_id` до переподключения. Повторять с тем же ключом только после сверки.
8. **Production DONE:** `project_deploy_status(deployment_id)` должен показать `succeeded` и точную `installed_version`; затем `project_verify(expected_version=<new>)` и независимое подтверждение хешей реально работающих controller/broker, readiness tunnel, DNS/HTTPS, защищённых соседних сервисов и возможности rollback. В конце cleanup своих временных материалов, статус ROADMAP и issue acceptance — только по evidence. Нельзя выдавать CI/build/plan/stage за установленную версию.
9. **Резервный локальный маршрут:** когда проверенного GitHub-артефакта действительно нет, допускается `release_build_prepare` из immutable protected main плюс **успешный FENCED test permit** того же commit → `release_apply`. Отсутствие test success, client policy block, UNKNOWN или отсутствие Face ID запрещает `release_apply`; не обходить через RDC, SSH, root, `tool_invoke` или shell. `release_local` не требуется, если `release_apply` сам безопасно читает sealed paired images.
10. **Восстановление:** зависшая стадия = reconcile исходного job/deploy ID, lease и receipt; `NOT_STARTED` и отсутствие release plan не означают разрешение ручной замены бинарников. Если один независимый авторизованный маршрут заблокирован, проверь существование другого с отдельной собственной цепочкой admission+CI+rollback+verification. При чужом lease — собственный свободный sibling worktree или HOLD, без перехвата, нарушения fencing и второго production writer.

Совместимость состояния при откате: новые workflow используют схему `mcpshka.workflow/v2` и отдельный fingerprint плана. Reader 0.8.1 отвергает такие записи своим прежним контролем fingerprint: он не умеет соблюдать новые паузы и дедлайны. Это ожидаемый HOLD с сохранением задачи; вернуть 0.8.2 и продолжить по исходным ID/receipts. Не удалять запись, не снимать паузу и не создавать повторный запуск ради отката. Старые workflow 0.8.1 без этой схемы продолжаются в 0.8.2 по прежнему fingerprint; перед подключением новых mission controls такой workflow нужно завершить. Этот контроль формата не заменяет проверку пары controller/broker, jobs, leases и production smoke.
