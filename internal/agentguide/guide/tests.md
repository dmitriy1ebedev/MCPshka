# Тесты

- `project_test path=<repo>` — тест из профиля проекта в изолированной песочнице: все отслеживаемые файлы коммита HEAD, без сети, только чтение, scratch на диске, 200% CPU с низким приоритетом. Нужен закоммиченный и чистый HEAD: правки (`fs_write`/`fs_patch`) фиксируй `project_commit path files message lease_token` — сырой `git` через `exec_start` не нужен. Тест профиля — закоммиченный исполняемый скрипт `./tests/run.sh` или голая команда (`go`, `make`), не `sh script`.
- Не задавай `timeout_seconds` меньше прошлой успешной длительности: MCPshka поднимет лимит сама и напишет об этом в `plan.reason`.
- `job_wait job_id=…` в цикле до state ≠ running (один вызов ждёт до 45 с); результат — `exit_code` и вывод. Ожидание — не конец хода (rules п. 16).
- `packages`/`run` — точечный прогон Go-пакетов при разработке; для гейта фазы нужен полный тест (без фильтров).
- **Зависимости проекта MCPshka собирает сама.** Есть `requirements*.txt` → venv, `package.json` + `package-lock.json` → `npm ci`. Окружение собирается один раз в отдельной песочнице с сетью, кэшируется по хэшу файлов зависимостей и доступно тесту только на чтение в `/env` (`PATH`, `VIRTUAL_ENV`). Тест сам по себе — без сети. Если проекту нужен свой путь к интерпретатору — переменная в `env` профиля (например `LANE_TEST_PYTHON=/env/bin/python`).
- Тяжёлые наборы идут по одному: если хост занят, запуск подождёт сам.
- Гейт фазы засчитывает полный тест **точного** HEAD: sealed `project_test`, зелёный CI GitVerse проекта или полный `go-test` раннера (`DONE`); после нового коммита — повторить. Порядок выбора — rules п. 14.
- Изолированный тест модуля (`integration_test_prepare evidence=module`) после записи результата закрывается сам (fence брокера); если `next_action` предлагает `canary-fence` — выполни его, не жди юнит.
